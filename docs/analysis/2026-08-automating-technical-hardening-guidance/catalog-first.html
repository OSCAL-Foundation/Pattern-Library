Catalog-first

In this approach, the rule is a control in a catalog represented as a property named TechnicalControlID. The check is captured as a property named ConfigRuleId. The control states the requirement and the component captures the software that implements the requirement.

1. The stakeholder mapping

Three readings of what a hardening rule is are on the record, and this approach reads it as a requirement, which puts it in the Control layer, in the catalog model. That is what decides the table below.

Seven parties touch a hardening rule between a published guide and an audited system, and each works in an OSCAL model. Two sets of them are grouped: the bodies that author guidance, and the automation.

2. Strengths and risks with this approach

Considerations when introducing technical hardening controls as a catalog have been captured

2.1 Strengths4

  1. Requirements of any kind stay in one model

    Technical requirements are defined in the catalog and tracked through the remaining models exactly as regulatory controls are.

  2. Rules can be tailored

    A profile gives a hardening guide organizationally defined parameters and selects the part of it an organisation holds itself to.

  3. The catalog absorbs the shape of real guides

    Controls, parts and nested groups carry checks, remediation and prose at the scale of a thousand-page guide.

  4. The mapping is a document someone else can write

    The tie to a framework is its own mapping-collection, so a third party can publish it without owning either catalog.

2.2 Risks3

  1. More models to keep

    Benchmark requirements join the regulatory controls the plan of record already answers, and whether each new catalog needs its own plan is unsettled.

  2. More complexity to resolve

    Several frameworks and several benchmarks multiply catalogs, profiles and mappings, raising the entry cost for tools and producing hard profile resolution cases.

  3. The response cannot be made per instance

    A response is a by-component, so it names a component and never an instance, and one exception among a hundred hosts cannot be recorded.

3. Tracing rules and checks from implementation to assessment

The chain starts where the rule is introduced and runs to the claim and the result. What a step costs is how many relationships it is made of and how each one resolves.

  1. Rule, as it is introduced. The rule is a control in a product catalog, in the same model and the same shape a regulatory control has. Every step below starts from that id. catalog, controls[].id.
  2. Rule →to Check. Two ties, opposite ways. The control names its check by title, which no schema can check; the check names its control by id, which resolves.
  3. Rule →to Control. A document of its own, written after both catalogs and by someone who owns neither.
  4. Check →to Runtime. The prop names the rule the engine runs. The engine itself is nowhere in the content.
  5. Runtime →to Claim. The claim is against a component, not a host. A by-component takes no subject.
  6. Claim →to Result. The finding targets the statement in the plan of record, which is what makes it an answer to the claim.

This site makes no recommendation. It states three approaches in the terms their proponents use and shows the content each one ships.
