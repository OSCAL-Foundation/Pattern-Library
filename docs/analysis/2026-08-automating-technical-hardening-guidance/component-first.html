Component-first

In this approach, the rule is a rules entry on the component it configures, and the check is a checks entry on a second component of type validation. The component states what must be true and the validation component states how it is tested.

1. The stakeholder mapping

Three readings of what a hardening rule is are on the record, and this approach reads it as a capability statement, which puts it in the Implementation layer, in the component-definition model. That is what decides the table below.

Seven parties touch a hardening rule between a published guide and an audited system, and each works in an OSCAL model. Two sets of them are grouped: the bodies that author guidance, and the automation.

2. Strengths and risks with this approach

Considerations when introducing technical hardening rules into a component definition have been captured

2.1 Strengths4

  1. One artifact serves the reader and the tool

    A component definition says how a component can meet a control, the world of possibility for software, and rules inside it make that document drive automation.

  2. The rule and the check are separate things

    The rule sits on the product and the check on a second component, so a second engine is a second component.

  3. The claim can name the rule it rests on

    The proposed implementing-rules closes the distance between saying a control is implemented and saying which rule implements it.

  4. Vendors already have advice for this model

    Vendors are told to describe how their product can meet requirements in a component definition, so the rules land in one model.

2.2 Risks5

  1. Four models have to change

    The proposal changes the component definition, the plan of record, the assessment plan and the result, so today it is a proposal.

  2. Desired state enters the plan of record

    Rules describing how a component should be configured join a document whose job is to say how the system actually is today.

  3. The fidelity fields are proposed, not carried

    Rationale, audit procedure and remediation are most of a published guide, and the shipped rules carry none of them.

  4. The response is still not per instance

    An exception reaches a rule but still not an instance, because the response is a by-component here too.

  5. Inventory items may need it too

    For a claim to reach a host rather than a class, implementing-rules would have to be carried by inventory items as well.

3. Tracing rules and checks from implementation to assessment

The chain starts where the rule is introduced and runs to the claim and the result. What a step costs is how many relationships it is made of and how each one resolves.

  1. Rule, as it is introduced. The rule is a first-class entry on the component it configures, so it is introduced inside the document that describes the thing being hardened. Every step below starts from that id. component-definition, components[].rules[].id.
  2. Rule →to Check. Both halves of the key sit on the check side. A rule id is unique only inside the component that declares it.
  3. Rule →to Control. Both sides in one document. The control implementation already ties component to control; naming the rule inside it is the proposal.
  4. Check →to Runtime. The checks are inside the component that runs them. A second engine is a second component.
  5. Runtime →to Claim. The claim names the rule it rests on, so a reader gets from claim to check without leaving OSCAL.
  6. Runtime →to Result. The observation names the check and the host, so two machines in one boundary can disagree and both be recorded.
  7. Result →to Control. The result never states the control. It carries observations and no findings, so there is no status to hold one.

This site makes no recommendation. It states three approaches in the terms their proponents use and shows the content each one ships.
