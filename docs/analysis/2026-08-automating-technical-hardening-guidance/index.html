1. One recommendation, three paths

Hardening guidance is written by one party, applied by a second and checked by a third, and one recommendation goes down all three paths rather than along one of them. What each party needs from it differs, and where the recommendation is written decides how much of that need it can meet.

The three paths start from the same place and none of them passes through another. The assessor's in particular can be run independently of the implementer's: an assessor takes the recommendation and brings their own means of checking it, so nothing the implementer produced has to exist first.

2. Implementation and assessment layers are both viable for a hardening recommendation

A recommendation results in a rule that can be introduced in two OSCAL layers. Each option below answers where the rule is written, where the check is written, and where the response is recorded.

Implementation Layer

Shift left, so implementers can use it

The rule and its check are written where the implementer can reach them. Both options record the response in the system security plan, and they differ in which model holds the rule.

Catalog-first  Rule in Catalog
  • Rule a control in a product-specific catalog
  • Check a check in a component definition
  • Response system security plan
Component-first  Rule in Component Definition
  • Rule a component definition
  • Check a check in a component definition of type validation
  • Response system security plan
Shared by both paths Check Runner

The check and runner

A rule names a check with a runner executing the check. The same automation can serve an implementer analysing an environment and recording its state, or an assessor producing a result.

Assessment Layer

Write the rule and the check in the assessment

The assessment plan holds the check, and the rule is written into the same plan as an activity and a step in plain English. The response is recorded as an assessment result rather than in the system security plan.

Assessment-first  Assessment plan and assessment results
  • Rule an activity or a step in the assessment plan, in prose
  • Check a check linked directly to the rule
  • Response assessment results

Assessors may automate assessments of environments directly or assessment of security packages. In either case, assessors do not rely on system owner defined hardening guidance to conduct assessments. They will bring their own assessment capabilities, independent of any features available through the system

5. Why question 6 splits: a claim is not a result

Question 6 is broken in two, 6a and 6b. Asking whether a rule is satisfied turns out to be two questions answered by two stakeholders. An implementor uses a system security plan to capture how a control is satisfied, in narrative, as standing design intent, asserted by the system owner. An assessment result captures whether it was satisfied, at a point in time, on a named subject, asserted by the assessor.

This site makes no recommendation. It states three approaches in the terms their proponents use and shows the content each one ships.
